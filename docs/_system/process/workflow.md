# Documentation workflow

This is the canonical process for documentation assessment, authoring, normalization, review, and retirement. Read `docs/_system/constitution.md` first; it governs every judgment.

## Authority

Documentation-only work may inspect the repository but may modify only `docs/`. It never fixes code, tests, scripts, workflows, configuration, infrastructure, schemas, or deployed state. Validation is repository-only; never query live or external systems. Report implementation concerns in the task result and create no issue or findings file without separate authorization. The lifecycle commands specified in [`../lifecycle.md`](../lifecycle.md) are the exceptions; their authority is defined there.

## Agent interface

Supported actions are `install`, `upgrade`, `configure`, `remove`, `uninstall`, `assess`, `create`, `update`, `rename`, `move`, `retire`, `intake`, `review`, `check`, `fix`, `explain`, and `audit`. The prose form `OttoDoc <action>` is the portable way to invoke any of them in any supported agent interface, and the only form for `install`, which necessarily runs before any adapter exists. Treat it, or a plain request that plainly asks for the action ("create a runbook for rotating the key"), as an explicit request to use this documentation engine; the action's definition is in this file and the files it points to, whether or not an adapter exists.

Five actions also have a slash command in each configured platform — `/ottodoc-<verb>` in Claude Code and Cursor, and the `ottodoc-<verb>` skill in Codex, invoked as `$ottodoc-<verb>` because Codex has no repository-level slash commands: `intake`, `assess`, `audit`, `upgrade`, and `uninstall`. A verb earns a command only when the owner must choose to trigger it, it orchestrates several roles, and a plain request would not reliably reach it. The commands are conveniences; nothing is defined only in an adapter. The agent selects the applicable workflow, roles, templates, and deterministic tooling from the action and the instructions that follow it. `Update` edits a knowledge document, and `rename` changes only a concept filename while repairing links and regenerating indexes.

### Lifecycle commands

`install`, `upgrade`, `configure`, `remove`, `uninstall`, and `check` manage the installation itself and are specified canonically in [`../lifecycle.md`](../lifecycle.md) — read it before executing one. Two workflow rules apply on top of that spec:

- A lifecycle command frequently arrives from an agent with no prior OttoDoc context. Do not assume the engine was already discovered in this session: locate it under `docs/_system/`, read `lifecycle.md`, then proceed. If `docs/_system/` is absent, OttoDoc is not installed and the correct action is `install`.
- The platform name for `configure` and `remove` is always required — never infer it, never treat a missing name as "all of them", and never escalate `remove` to `uninstall`. Confirm with the owner before invoking `uninstall`; the script itself is non-interactive so that other commands and CI may call it.
- The intake setting (`archive` or `delete`, specified with the record in `lifecycle.md`) is the owner's to state. When an install request does not state it, ask before installing. When the owner asks to change it later, in any words, rewrite the `intake:` line of `docs/.ottodoc` and nothing else.
- Relay every `CREATED:` and `NOTE:` line a lifecycle command prints to the owner, in substance and not merely as "succeeded". Those lines announce changes in behavior — a new system boundary, a one-time line-ending artifact — that the owner is entitled to decide on rather than inherit.

`OttoDoc intake [filename]` accepts one optional filename: one filename processes that direct child of `docs/_intake/`, while no filename processes the entire folder. Do not require users to name or invoke implementation scripts. Scripts remain available to agents, maintainers, and CI as the execution layer.

## Agent-driven work

By default no role is dispatched before a system-modifying change lands. The working agent files a change note instead. When the first system-modifying task in the change completes, it reads the `subject:` frontmatter line of each change note directly in `docs/_intake/`, never under `archive/` — that line alone, not the notes — and if one concerns the same feature, behaviour, or decision, it revises that note; otherwise it creates `docs/_intake/change-<YYYY-MM-DD>-<slug>.md` from `docs/_system/templates/change-note.md`, dated at creation, slug drawn from the change's purpose. As later tasks finish it keeps the note stating the net change, rewriting what a later task revised or reversed rather than adding beneath it, so the tasks' documentation-impact notes accumulate in a file rather than in reports that context compaction can drop, and one subject never waits in intake as several notes. The note records only what the agent verified, and quotes any human or external source verbatim with what identifies it — a time, message id, subject, or path. Two branches that revise the same note can conflict when they merge; resolve it like any conflict, into one note stating the net change. The note is a lead for the coordinator, not a draft document: it records what the code cannot reveal, and the code itself is read at processing time. Before the change lands — before it is committed or raised as a pull request — the note is current, and it lands in the same commit as the code. The agent writes it at its own reasoning level; the coordinator, author, and reviewer are not summoned. Formatting-only, comment-only, generated-only, Git-only, and documentation-only changes need no note, so the documentation change that intake processing produces is itself exempt. Neither does a change confined to paths outside the system boundary (constitution §8) — `docs/`, Git's own files, and whatever `docs/.ottodocignore` lists — and a mixed change's note leaves those paths out.

Dispatch `doc-coordinator` for `OttoDoc assess`, for `OttoDoc intake`, and for every agent-driven documentation request. `assess` is the immediate path: the coordinator assesses the current change — the branch diff against its merge base together with the working tree — now, for an owner who wants a particular change's documentation authored before it lands; a change assessed this way owes no note, and a note the change itself created is consumed like any other intake source; a waiting note the change only revised stays in intake, because it still carries earlier changes this assessment did not cover. `intake` is the deferred path: the coordinator assesses every change note and human draft in `docs/_intake/`, or the one named, on the owner's schedule. On either path the coordinator assesses impact itself and may conclude that no documentation change is justified. When work is needed, it dispatches `doc-author`, then a fresh-context `doc-reviewer` that reviews the change rather than every document it touched, re-dispatching the author with any blocking findings for at most two revision cycles — and one final pass when every remaining finding is an exact correction needing no judgment — before asking the owner. Intake is processed one source at a time, and each source's documentation is committed on its own before the next begins.

Dispatch is a call that returns. Each role delivers its report as its final response to whoever dispatched it, and the coordinator collects every result itself rather than ending its turn to wait for one. Roles never message each other by name, because a role name identifies a definition rather than a running agent.

The coordinator, author, and reviewer retain the authority boundaries in their canonical definitions under `docs/_system/process/`.

## Audit

`OttoDoc audit [scope]` is the owner's on-demand sweep of the existing knowledge tree for quality debt that no single change surfaces: facts retold across documents, kind drift, change-process language, stale or wrong claims, and documents grown past their size triggers. The scope is one path under `docs/` — a document, a kind directory, or a subject subfolder — or, when omitted, the whole tree; reject multiple scopes and patterns. It runs only when the owner asks — nothing schedules it, in keeping with the constitution's rejection of staleness timers — and it changes no file until the owner approves a unit's fixes.

The cost of an audit must never depend on how large the tree is, so it is processed one **unit** at a time, and the owner sees each step as it happens. `doc-coordinator` runs it in three stages:

1. **Map.** Before reading any document in full, build the map of the scope mechanically and show it in chat. The units are the subject subfolders of each kind and the documents directly in a kind directory, each named by its directory path; a unit of more than ten documents is split in filename order into parts named `<path> part <n>`. List the units in order with each one's document count and word count and whether it is already audited, and add the mechanical results: run lint and `regen.ps1 -Check` and report their output, including any warnings lint prints — a failure is a finding like any other, and the audit continues. Also search the scope for facts stated in more than one document, for documents whose content does not fit their kind (constitution §2), for titles joined by "and", and for documents past the size triggers. These are candidates, not conclusions; each goes to the first unit in map order that holds one of its documents. A unit is audited when its latest commit with the subject `docs: audit <unit>` is newer than every other commit that touched any of its documents. That derivation is the only progress record: no file keeps it (constitution §6), a unit with no findings leaves no commit and is reviewed again on a later run, and a unit whose documents have changed since is unaudited again.
2. **Review.** Take the unaudited units in map order, one at a time. Say which unit is next, its position, and its size; dispatch a fresh-context `doc-reviewer` with its documents and its candidates. The reviewer reads every document in full against its criteria and spot-checks a few concrete claims per document against the repository, reporting every finding, not only those in a change's delta. Report that unit's findings in chat as soon as the reviewer returns, grouped by document, each naming the criterion it violates and a concrete correction, with a running count of units done and findings found. Create no file and no issue (constitution §6).
3. **Fix.** Ask the owner which of the unit's findings to apply — all, a chosen subset, or none — and whether to continue afterward. Approved findings become a delta for the normal loop. Confirm first that the knowledge tree holds no uncommitted change, because the unit's documentation is committed on its own. Then the coordinator lists the documents already mentioning the same facts, dispatches `doc-author`, then a fresh-context `doc-reviewer`, with at most two revision cycles before asking the owner. The documents the findings name are the delta's whole scope, including any that sit in another unit. Once review passes and the mechanical checks are green, dispatch the author to commit the unit under the subject `docs: audit <unit>`, then continue with the next unit unless the owner chose to stop.

The owner may stop at any unit boundary. A unit is either committed or untouched, and a later `OttoDoc audit` rebuilds the map, shows which units are audited, and resumes with the first that is not. To work one unit out of order, name it as the scope.

## Intake sources

`docs/_intake/` is one flat folder holding two kinds of source side by side. Humans may place rough documents and external material there without conforming to the final structure. Agents file change notes there, recognized by the `change-` filename prefix. Filenames must be unique; add no directories other than the `archive/` folder that consumption creates. Placement is inert. `OttoDoc intake <filename>` routes that one direct child through the coordinator; `OttoDoc intake` routes every file currently in intake. Reject paths, directories, multiple filenames, and filename patterns.

For a human draft, the author preserves intended meaning and human-provided external facts while normalizing kind, scope, summary-first structure, concision, links, and frontmatter; material ambiguity returns to the owner. For a change note, the coordinator assesses the change the note describes against current repository state. Sources are processed one at a time in filename order; only change notes on one subject, or where a later change absorbs or reverses an earlier one, are processed together. Consumed sources are deleted or archived, as the installation's intake setting directs (constitution §6), in the same docs change as the documentation they produced, or in a consumption-only docs change when none is produced. A human draft that yields no document is archived without approval but deleted only with the owner's approval; a change note is consumed on either outcome without it. `docs/_intake/archive/` is never processed.

## Direct maintainer workflow

Maintainers may scaffold or edit documentation directly when they need the underlying execution layer. Agent normalization and fresh-context review follow before completion.

- Scaffold: `docs/_system/scripts/scaffold.ps1 -Kind <runbook|reference|decision|explanation|plan|design> -Slug <kebab-slug> -Title "<Title>" -Actor "<actor>" [-Subject <kebab-subject>]`
- Rename: `docs/_system/scripts/rename.ps1 -Path <knowledge-file> -Slug <new-kebab-slug>`
- Lint: `docs/_system/scripts/lint.ps1`
- Regenerate: `docs/_system/scripts/regen.ps1`
- Prove current: `docs/_system/scripts/regen.ps1 -Check`
- Verify adapters: `docs/_system/scripts/check-adapters.ps1`

Never hand-edit an `index.md`. A material content change updates `generated`; a typo-only or relocation-only change does not. Moves and deletions include fixing inbound links and dissolving empty subject folders. Documents and regenerated indexes land together.
