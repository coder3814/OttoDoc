# OttoDoc portability design (resolved)

Supersedes the earlier consolidated design. Every open item is now decided; the
decisions and their reasoning are recorded in §10. This document lives outside
`docs/_system/`, so it is not part of the vendored engine and does not ship into
consuming repositories.

**Goal:** an owner can install OttoDoc into a repository on any supported agent
platform, add or drop platforms over time, and remove OttoDoc entirely, using only
OttoDoc's own commands - and the documentation contract holds identically on Claude,
Codex, and Cursor.

**Status:** designed and decided. Implementation still requires the repository owner's
explicit go-ahead (constitution §3 guard, §8 approval rules).

---

## 1. Command surface

| Command | Argument | Effect |
|---|---|---|
| `OttoDoc install <platform>` | required | Unchanged. Fetches the engine, configures one platform, creates the tree, generates navigation and CI. |
| `OttoDoc configure <platform>` | required | **Additive.** Adds one platform to the configured set, leaving others untouched. |
| `OttoDoc remove <platform>` | required | **New.** Decommissions exactly one platform. Never escalates. |
| `OttoDoc uninstall` | none | **New.** Removes the engine and every platform. |
| `OttoDoc upgrade` | none | Refreshes the engine and **every configured platform**, not just one. |

Rules:

- `remove` always requires a platform name; invoking it without one is an error, never
  a default to "everything." The blast radii of `remove` and `uninstall` are not
  comparable, and the argument is extracted by a language model from a loose sentence.
- `remove` on the only configured platform is **allowed** and leaves OttoDoc installed
  with zero configured platforms. There is no offer to uninstall and no escalation.
  Zero platforms is an ordinary state: the engine is still on disk and CI still runs,
  and anyone can restore a platform by pasting a `configure` command from the README.
- `install` still configures exactly one platform. Additional platforms come from
  `configure`.
- `uninstall` is a separate command from `remove` even though they share an
  implementation - the same relationship `install` already has with `configure`.

## 2. File ownership model

Every platform's adapter set has the same shape: **one shared always-on file carrying
an OttoDoc marker block, plus platform-owned files OttoDoc writes whole.**

### Owned files - whole-file generation

OttoDoc creates and deletes these outright. They live at OttoDoc-specific paths.

| Platform | Owned paths |
|---|---|
| Claude | `.claude/agents/doc-coordinator.md`, `.claude/agents/doc-author.md`, `.claude/agents/doc-reviewer.md`, `.claude/skills/doc/SKILL.md` |
| Codex | `.agents/skills/documentation/SKILL.md`, `.codex/agents/doc-coordinator.toml`, `.codex/agents/doc-author.toml`, `.codex/agents/doc-reviewer.toml` |
| Cursor | `.cursor/rules/documentation.mdc`, `.cursor/skills/documentation/SKILL.md`, `.cursor/agents/doc-coordinator.md`, `.cursor/agents/doc-author.md`, `.cursor/agents/doc-reviewer.md` |
| all | `.github/workflows/docs.yml` |

**Owned files carry no generated-by stamp.** Ownership is established by two conditions
together: the path appears in the authoritative map, and the file's content matches what
current canon renders for that path. A file at a known path that does not match canon is
reported, never deleted and never overwritten.

### Shared files - marker-block contribution

These sit at paths other tools and the owner also use. OttoDoc contributes a delimited
block, creating the file only if absent, and never owns the rest of it.

| Platform | Shared file |
|---|---|
| Codex | `AGENTS.md` |
| Claude | `CLAUDE.md` |

This replaces today's behavior, where `configure` generates the whole `AGENTS.md` and
refuses to run if a non-OttoDoc one already exists - which would fail in most real
repositories.

**Block form:**

```
<!-- ottodoc:begin - generated by OttoDoc. Do not edit inside these markers. -->
## Documentation engine

After every completed system-modifying task, read `docs/_system/process/coordinator.md`
and perform its bounded documentation-impact assessment. Follow
`docs/_system/constitution.md` for every documentation judgment. Use the
`doc-coordinator`, `doc-author`, and `doc-reviewer` subagents when the canonical
workflow requests those roles.
<!-- ottodoc:end -->
```

Marker rules:

- The parser matches on the bare `ottodoc:begin` and `ottodoc:end` tokens, **not** on the
  full marker line. If it required the whole line, rewording the "do not edit" prose in a
  later engine version would fail to find blocks already installed in the field and would
  append a second one beside each.
- Two OttoDoc blocks in one shared file is a hard error, not a take-the-first. That state
  only arises from a bad merge, and silently resolving it discards content.
- HTML comments are invisible in every mainstream Markdown renderer, including GitHub.

Constraints on block content, which §8 already makes law - platform files outside
`_system/` are discovery adapters carrying no original process information:

- The block is a pointer plus a trigger. Every rule it references lives under
  `docs/_system/`.
- The only non-pointer content is the timing condition ("after every completed
  system-modifying task") and the platform's subagent names, which differ per platform
  (`doc_coordinator` for Codex, `doc-coordinator` for Claude) and so cannot be stated
  portably in the canonical files.
- No H1. The block lands inside a file that already has a title.

## 3. Claude parity

Configuring Claude writes a `CLAUDE.md` block carrying the same post-task assessment
instruction Codex and Cursor already get.

Rationale: §8 states the post-task documentation-impact assessment as law - every
completed system-modifying task receives one. Codex gets it from an always-on
`AGENTS.md` and Cursor from `.cursor/rules/documentation.mdc` with `alwaysApply: true`.
Claude's adapter set is subagents plus a skill, which is entirely pull. `CLAUDE.md` is
Claude Code's only always-on surface, so push behavior is impossible without it. Until
now OttoDoc enforced its own §8 on two of the three platforms it claims to support.

Consequences:

- §8's sentence declining a `CLAUDE.md` is overturned and deleted.
- `docs.yml` path globs must add `CLAUDE.md`. They currently list `AGENTS.md` only, so
  an edit to Claude's block would not trigger the check that would catch it.
- Drift checking must be block-aware for both shared files: verify OttoDoc's block
  against canon while ignoring everything the owner wrote around it.

## 4. Cold start

**The README is the discovery surface, and the human is the bridge.** No stub adapters,
no configuring every platform by default.

An owner who opens Claude Code in a Codex-configured repository copies the configure line
out of the README and pastes it. That is the same interaction install already uses -
`OttoDoc install Codex from https://github.com/coder3814/OttoDoc` is already a line
copied from a README into an agent that has never heard of OttoDoc, and the trailing URL
is what makes it self-sufficient.

Work required is documentation only:

- A README section for adding an agent platform to an existing installation, giving the
  plain `OttoDoc configure Claude` form first and the `from <URL>` form as the fallback
  when the agent does not recognize the command. This mirrors the pattern the README
  already uses for the upgrade transition at `README.md:270-276`.
- `workflow.md` must state that `OttoDoc configure <Platform>` may arrive from an agent
  with no prior OttoDoc context, so the configure workflow locates the installed engine
  under `docs/_system/` rather than assuming it was already discovered.

**Accepted residual:** an agent on an unconfigured platform stays blind until a human
pastes the command, so a teammate who never reads the README can hand-write documentation
past the contract. The consequence is bounded by design - CI runs lint and index-drift
checks on every change to `docs/` regardless of which tool authored it, so that person
gets a failing build rather than silently corrupting the tree. Enforcement is
trigger-independent; only discovery depends on a human.

## 5. Uninstall

`OttoDoc uninstall` removes the engine and leaves the documentation.

**Removes:**

- `docs/_system/`
- `.github/workflows/docs.yml`
- Every owned adapter path for **all supported platforms**, not only configured ones -
  deleting a file only where content matches canon, and reporting anything at a known
  path that does not match instead of touching it. This cleans up adapters stranded by
  the current buggy `configure`, without ever deleting a file OttoDoc did not write.
  Note the bound: adapters stranded by the *current* engine were written from current
  canon and so match and are deleted, but adapters stranded by an older engine whose
  canon has since changed are reported rather than removed.
- OttoDoc's marker block from shared files, deleting the file itself only if nothing
  else remains in it.
- The governance blockquote line that `regen.ps1` emits into the root index. This is
  uninstall's only edit inside `docs/`, and it exists so no dangling link to a deleted
  constitution is left behind.

**Preserves:** all documents, all generated indexes, all assets, and `docs/_intake/`
with its contents.

**Safety:** the agent confirms with the owner before running. The script itself is
non-interactive, so other commands and CI can call it. The result is left as an
uncommitted diff for review, exactly as `upgrade` behaves today. Git is the undo; no
backup-and-rollback machinery.

**Reinstall needs no new machinery.** After uninstall the tree is still conformant, so
`bootstrap.ps1` creates the missing kind directories (all no-ops), configures the named
platform, and regenerates - and because regen is deterministic, every index is restored
byte-identically, governance pointer included. The marker-block model is what makes this
safe: an owner who wrote their own `AGENTS.md` during the uninstalled period would have
hit the old whole-file refusal, but a block simply appends.

The one failure mode is drift while unmanaged. If documents were hand-written without
frontmatter while OttoDoc was gone, bootstrap's lint gate fails and refuses, modifying
nothing. That is correct behavior, and the owner is not stuck - `docs/_system/` is
already on disk by then, so lint's findings are available to work through. Worth stating
in the README's install section rather than leaving people to meet it as an error.

## 6. The structural fix underneath everything

The single largest cause of the reported gaps is that **the platform-to-files map exists
in three places with three different scopes**: `configure-platform.ps1:25-49` (one
platform), `upgrade.ps1:38-60` (all three, then narrowed to one), and `docs.yml`'s path
globs (all three, never narrowed). The stranded-adapter finding, the narrowed-upgrade
finding, and the CI asymmetry finding are not three bugs - they are one duplicated table
drifting apart.

Required:

1. **One authoritative map in `common.ps1`**, consumed by configure, remove, uninstall,
   upgrade, and CI-workflow generation. It must distinguish owned paths from shared-file
   blocks.
2. **`Get-ConfiguredPlatforms`** - read the configured set from the per-platform check
   steps in `.github/workflows/docs.yml`. See §10 for why this rather than file presence.
3. **One shared decommission routine**, content-verified, used by `remove` for one
   platform and by `uninstall` for all of them.
4. **`upgrade` refreshes every configured platform**, replacing today's
   `$managedTargets = @($platformTargets[$Platform]) + ...` narrowing.
5. **CI emits one check step per configured platform.** `docs.yml` is therefore rendered
   from the configured set rather than produced by a `{{PLATFORM}}` substitution, and
   `configure`, `remove`, and `uninstall` all regenerate it.
6. **An orphan-adapter check in CI**: every adapter file present on disk must belong to
   a configured platform and match canon. This is what makes the broad path globs correct
   rather than a source of green checks on unverified files. In a zero-platform
   repository every adapter file is by definition an orphan, so anything the decommission
   sweep missed fails the build instead of rotting quietly.

### Script signatures

One job per script:

| Script | Signature | Job |
|---|---|---|
| `configure-platform.ps1` | `-Platform <X>` | Add or refresh one platform |
| `remove-platform.ps1` | `-Platform <X>` | Decommission one platform |
| `check-adapters.ps1` | *(no arguments)* | Verify the whole adapter invariant |
| `uninstall.ps1` | *(no arguments)* | Remove the engine and every platform |
| `upgrade.ps1` | *(no `-Platform`)* | Refresh engine and every configured platform |
| `bootstrap.ps1` | unchanged | Install |

`check-adapters.ps1` takes no arguments because the check's scope is defined by installed
state, not by a caller. "Every adapter file on disk belongs to a configured platform and
matches canon" is a single invariant; splitting it into a per-platform check plus a
separate orphan check is what produced §6.6's awkward "`-Platform` becomes optional in
check mode."

`upgrade.ps1` loses `-Platform` outright rather than making it optional. Optional leaves
the narrowing behavior reachable as an opt-in, and neither reading of the flag is wanted:
"refresh only this one" is the bug being fixed, and "also add this one" is `configure`'s
job. An empty detected set means the engine and indexes refresh and no adapters do, which
§1 already declares an ordinary state.

## 7. Migration constraints

These are not design choices; they are conditions for existing installations to reach the
new engine at all.

**`configure-platform.ps1` must keep accepting `-Check`** as a shim that delegates to
`check-adapters.ps1` and ignores `-Platform`. The script that performs a transition
upgrade is the *old* `upgrade.ps1` already installed in the field, and it calls
`& $configure -Platform $Platform -Check` at `upgrade.ps1:186` against the *new* engine.
Without the shim that call fails, the `catch` fires, and every existing installation
rolls back rather than upgrading - with an opaque error and no path forward, since the
documented `OttoDoc upgrade from <URL>` transition runs the same old script and fails
identically. The shim is removable once installations have moved.

**The `docs.yml` set parser must read both shapes.** During a transition upgrade,
`Get-ConfiguredPlatforms` runs against the *old* `docs.yml`, whose single check step
renders as `-Platform Claude -Check`. If the parser only understands the new
per-platform steps, the first upgrade detects zero platforms and refreshes no adapters,
silently.

**Rollback during a transition upgrade is incomplete.** The old `upgrade.ps1` backs up
only `$managedTargets`, which does not include `CLAUDE.md`. If the new `configure` writes
a Claude block and a later step fails, the old rollback restores everything except that
block. Bounded to the one transition upgrade; worth a note in the README rather than
machinery.

## 9. Deferred

**Versioning.** No engine version exists today; the only version in the system is OKF
0.2, which versions the knowledge format rather than OttoDoc. Deliberately not added.
The engine is vendored in full, so `git log -1 -- docs/_system/` answers "when was this
last upgraded," and because `upgrade` leaves an uncommitted diff, an empty diff answers
"am I current."

The real gap is provenance rather than versioning: `upgrade.ps1` downloads a zip of the
`main` branch, and a branch zip carries no commit identity, so nothing records which
upstream commit the installed engine came from. That matters only when someone reports a
problem and you cannot inspect their repository yourself. The cheap fix, if it is ever
needed, is a small generated file recording source repository, ref, fetch date, and
commit SHA - provenance without release discipline, changelogs, or compatibility
promises. Revisit on external adoption, not on elapsed time.

## 10. Decision log

Four items were open. All are now resolved.

### Ownership predicate for decommission

**Decided:** ownership is path-in-map plus content match against canon. No generated-by
stamp in owned files.

Rejected: a literal `ottodoc:` stamp in every owned file. The stamp would have satisfied
§5's stranded-adapter cleanup goal completely, because a file stranded by an older engine
still carries its stamp even though it no longer matches canon. The content-match rule
trades that tail case for a stronger guarantee: OttoDoc never deletes a file it did not
produce byte-for-byte.

Two consequences followed. The `docs.yml` header, which lacks the word "adapter" and so
would have failed a stamp-style predicate built on today's `(?i)generated[^\r\n]*adapter`
regex, needs no change at all. And §5's claim about cleaning up stranded adapters had to
be narrowed to the current-engine case.

### Detection of the configured set

**Decided:** `Get-ConfiguredPlatforms` reads the per-platform check steps in `docs.yml`.

The deletion predicate cannot serve as the detection predicate. During `upgrade` the
engine is replaced before anything else runs, at which point every installed adapter is
stale relative to new canon by definition; a content-match detector would return the empty
set and refresh nothing, silently. So detection must be weaker than deletion.

Rejected: file presence at known paths. With no stamp, a hand-written file at an OttoDoc
path is indistinguishable from a configured one, and combined with `configure`'s refusal
to overwrite non-matching files, a single stray file could wedge `upgrade` with a
confusing error.

`docs.yml` is not an inference: §6.5 already makes it list one check step per configured
platform, it is owned by OttoDoc, and it lives outside `docs/_system/` so it survives the
engine swap. Cost accepted: `docs.yml` is now state as well as output, and a hand-edit to
it corrupts the set.

This also settles a question that would otherwise have needed a constitution sentence. A
repo where today's buggy `configure Codex` stranded the Claude adapters detects as
Codex-only, which makes those files orphans - so `check-adapters.ps1` fails the build on
them rather than treating them as live. No §9 amendment is needed to say stranded
adapters count as configured, because under this rule they do not.

### Home of the adapter verification

**Decided:** its own script, `check-adapters.ps1`, taking no arguments.

Rejected: `configure-platform.ps1 -Check`, which keeps a mandatory parameter that is
silently ignored in one mode - the shape that produced the current confusion. Also
rejected: folding it into `lint.ps1`, which is about the knowledge tree and its
frontmatter contract, not adapters, and whose gate `bootstrap` relies on failing for a
different reason (§5).

### Uninstall script name

**Decided:** `uninstall.ps1`, matching the agent-facing command exactly, following the
`upgrade.ps1` precedent. An agent reading `workflow.md` has the least room to pick the
wrong script. Rejected: `teardown.ps1`, whose symmetry with `bootstrap.ps1` is misleading
since bootstrap also creates the tree, lints, and regenerates, none of which uninstall
reverses.

## 10a. Deviations found during implementation

Four things the design could not have settled on paper. All are implemented and covered
by the test suites described in §12.

**The configured set is recorded, not inferred from check steps.** §6.5 called for one CI
check step per configured platform, and the detection decision called for reading the set
from those steps. Those two are incompatible with the decision that verification takes no
arguments: an argument-free check step carries no platform name to read back. `docs.yml`
therefore carries an explicit generated record instead - `# ottodoc-platforms: Claude,
Codex` - plus a single argument-free check step. That is a better record than the one it
replaces: unambiguous, trivially parsed, and self-enforcing, because `docs.yml` is itself
content-matched against the rendering for the set it declares. Editing the record to add
a platform makes that platform's absent adapters fail as missing; editing it to drop one
makes its files fail as orphans.

**CI path globs stay broad.** They cover every supported platform rather than the
configured ones. Narrowing them would stop CI firing on an adapter belonging to an
unconfigured platform - precisely the orphan the check exists to catch. §6.6 implied
this; it is now stated in the template.

**`configure` replaces a non-matching owned file rather than refusing.** The ownership
rule - path in map plus content match - governs *deletion*, not writing. It cannot govern
writing, because during an upgrade every installed adapter is stale against new canon by
definition, so a refusal would make refresh impossible. Configuring a platform is an
explicit instruction to install its adapters at OttoDoc's own paths, so a differing file
there is replaced and the replacement is reported. Git is the undo, and the old
whole-file refusal's real purpose - not clobbering a genuine `AGENTS.md` - is now served
by the marker block instead.

**Legacy whole-file adapters are converted, not stacked under.** The pre-block engine
generated `AGENTS.md` whole and refused to run when the file was not its own, so the
marker it wrote on line 1 is proof it owned the entire file. On the first upgrade that
content is dropped and replaced by the block. Without this, every Codex installation in
the field would carry the old instructions duplicated above its new block permanently.

**`configure` writes every platform in the resulting set, not only the named one.** The
workflow records the set and `check-adapters.ps1` holds the installation to that record,
so writing only the named platform could leave a recorded platform whose files are absent
or stale - an installation that fails its own check immediately after configuring. This
bit hardest on the `CLAUDE.md` block, which no prior installation has. Writing the whole
set is a no-op for platforms already correct, and it keeps record and reality in step.

**Orphaned adapters are reported by `upgrade`, not fatal to it.** The pre-additive
`configure` is worse than the original gap report credited: adding a second platform
writes that platform's adapter files, then hits `.github/workflows/docs.yml` and refuses,
because its ownership test looked for the words "generated" and "adapter" on one line and
the workflow header has no such line. It exits non-zero with the new platform's files on
disk and the workflow still recording only the first platform. Those files are orphans
under the new rule, so a fatal orphan check would roll the upgrade back and strand exactly
the repositories that most need it. `check-adapters.ps1 -WarnOnOrphans` reports them
instead; `upgrade` and the deprecated `-Check` shim pass it, CI does not. The owner is
told both ways out - configure that platform to adopt it, or remove it to delete the
files - and OttoDoc chooses neither, because which platforms a repository should support
is owner intent and §9 forbids guessing it.

One bug was fixed in stride: `Get-DocsRoot` resolved its path with a `'..\..'` literal,
where a backslash is an ordinary filename character on Linux - the platform CI runs these
scripts on. It now uses two `Join-Path` hops.

## 11. Implementation constraints

- Scripts must run under Windows PowerShell 5.1 as well as `pwsh`. `configure-platform.ps1`
  is confirmed working under 5.1 on a box with no pwsh 7.
- Generated `.ps1` content must be ASCII-only. 5.1 mis-decodes UTF-8 without a BOM.
- Engine changes require the repository owner's explicit request (constitution §3 guard,
  §8 approval rules). This design was requested; implementation still needs the owner's
  go-ahead.

## 12. Verification

Two suites, both run under Windows PowerShell 5.1, both passing.

**Lifecycle.** A scratch repository through: install Codex; check; owner writes their own
content around the block; configure Claude additively; check with two platforms; plant an
orphan adapter for an unconfigured platform and confirm the check fails naming it; remove
Cursor and confirm the orphan is swept and the empty directory pruned; tamper with an
adapter and confirm the check reports it stale; remove Claude and confirm the tampered
file is reported and left while canonical files go, and that `CLAUDE.md` is deleted
because the block was all it held; remove the last platform and confirm zero platforms is
accepted with no escalation, the engine still installed, and the owner's `AGENTS.md`
content intact with only the block stripped; detect a legacy single-platform workflow;
uninstall and confirm documents, indexes and `_intake/` survive while the governance
pointer goes; reinstall and confirm the root index returns byte-identical.

**Migration.** An installation created by the engine at `git HEAD`, upgraded to this one
by the *old* `upgrade.ps1` already on disk. Confirms the `-Check` shim keeps that call
working, the workflow converts to the platform record, `AGENTS.md` converts to block form
with the legacy text dropped, an unrelated owner-written `CLAUDE.md` is untouched and gets
no block because Claude is not configured, and the adapter check passes afterward. Then a
second, steady-state upgrade with no `-Platform`, confirming both configured platforms are
refreshed rather than narrowed to one, and that the owner's `CLAUDE.md` content survives
the Claude block being added to it.

**Stranded adapters.** A repository where the pre-additive `configure` was used to add a
second platform - so its files are on disk but the workflow records only the first.
Confirms the old command really does fail that way, that the upgrade now completes and
reports the orphans rather than rolling back, that the orphaned files are neither swept
nor adopted silently, that a plain `check-adapters.ps1` still fails on them afterward with
both remedies named, and that either remedy resolves it: configuring the orphaned platform
adopts its files and records both, removing it deletes them, and in each case the other
platform is untouched.

Not covered by any suite: behavior on Linux under `pwsh`, which is where CI runs. The
`Get-DocsRoot` fix in §10a was found by reading rather than by testing, and no Linux
runner was available here.
